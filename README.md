# Job Search Assistant (Multi-Agent, Stage 5)

AI-агент, що допомагає аналізувати вакансії та готувати відгуки. Архітектура:
Orchestrator (LangGraph) координує спеціалізованих агентів.

Зараз є три агенти:

- **Researcher** — бере довільний текст вакансії та перетворює його у структуровані
  дані (назва, навички, рівень, вимоги до досвіду й англійської).
- **Analyst** — порівнює структуровану вакансію з профілем кандидата (`profile.json`)
  і дає вердикт: `apply` / `maybe` / `skip`, % збігу, що збігається, чого бракує,
  головні застереження та коротке пояснення українською.
- **Executor** — якщо вердикт `apply` або `maybe`, пише чернетку супровідного листа
  одразу двома мовами (англійською та українською) і зберігає у файл у папці
  `applications/`. Якщо вердикт `skip` — лист не пишеться (немає сенсу).

Якщо Researcher не впорався (помилка, порожній текст) — Analyst не викликається.
Якщо Analyst дав вердикт "skip" — Executor не викликається. Граф завершується
на тому етапі, де зупинився сенс продовжувати.

Кожен результат (вакансія + вердикт + шлях до листа, якщо був) зберігається в
історію в PostgreSQL — щоб бачити всі переглянуті вакансії в одному місці і не
аналізувати один і той самий текст двічі.

## Профіль кандидата

`profile.json` — дані про кандидата (цілі, досвід, навички, мова), які Analyst
використовує для порівняння. Відредагуй цей файл під себе: заповни навички,
роки досвіду, бажаний рівень англійської/італійської тощо.

## База даних (історія вакансій)

```
docker compose up -d
```

Піднімає PostgreSQL у контейнері (порт 5434 — щоб не конфліктувати з
Request Classifier, у якого PostgreSQL вже сидить на 5433). `cli.py` автоматично створює
потрібну таблицю при першому запуску. Якщо база недоступна (контейнер не
запущено) — `cli.py` все одно працює, просто без збереження в історію
(побачиш попередження в консолі).

## Запуск

```
pip install -r requirements.txt
cp .env.example .env   # встав свій GEMINI_API_KEY
docker compose up -d   # підняти базу (не обов'язково, але бажано)
python cli.py
```

Встав текст вакансії, заверши вводом Ctrl+D (Windows: Ctrl+Z, Enter).

## Тести

```
pytest -v
```

44 тести, LLM і база даних замокані (реальних викликів Gemini чи PostgreSQL
при тестуванні немає).

## Eval (перевірка якості Analyst)

`pytest` перевіряє КОД (retry, fallback, схему) на фейкових даних. Але код може
бути ідеальним, а промпт Analyst - почати давати погані оцінки (наприклад, після
зміни формулювань). Для цього окремий скрипт `run_eval.py`: невеликий набір
вакансій (`eval/cases.py`) із заздалегідь відомим "правильним" вердиктом
(apply/maybe/skip), прогнаний через СПРАВЖНІЙ Gemini (не мокано).

```
python run_eval.py
```

Виведе таблицю: очікуваний вердикт vs фактичний, % збігу, і підсумкову точність.
Потребує `GEMINI_API_KEY` в `.env` (реальні виклики дешевою моделлю, тому це не
частина `pytest -v` і не запускається автоматично). Якщо точність падає після
зміни промпту в `analyst.py` - сигнал, що щось зламалось.

## Структура

- `schema.py` — Pydantic-моделі `Vacancy`, `Analysis`, `CoverLetter`
- `researcher.py` — агент: структурує текст через Gemini, retry + fallback-модель
- `analyst.py` — агент: порівнює вакансію з профілем, retry + fallback-модель
- `executor.py` — агент: пише супровідний лист (EN+UK) і зберігає у `applications/`
- `candidate_profile.py` — завантажує `profile.json`
- `profile.json` — профіль кандидата (дані для Analyst та Executor)
- `orchestrator.py` — граф LangGraph: Researcher → Analyst → (Executor | кінець)
- `db.py` — зберігає історію вакансій/рішень у PostgreSQL (окремо від агентів)
- `docker-compose.yml` — контейнер PostgreSQL для історії
- `cli.py` — запуск з командного рядка
- `eval/cases.py` — набір вакансій з відомим правильним вердиктом (для eval)
- `run_eval.py` — прогін eval-набору через справжній Gemini, виводить точність
- `conftest.py` — порожній файл-маркер кореня проєкту для pytest
